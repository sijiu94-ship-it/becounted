## 二、Agent ID 应用说明

### 2.1 isHuman 如何工作

Agent ID 是币安 Agentic Wallet 的链上身份：按官方规则，一个 KYC 仅能领取一个、不可转让，登记在官方注册合约中：

- 官方注册表（SPACE ID Agent ID，BSC 主网）：`0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F`

BeCounted 的核心只有一个只读函数：

```
isHuman(address) -> bool   // 读取注册表 balanceOf(address)，> 0 即持有 Agent ID
```

性质（评审可在 BscScan 当场验证）：**无状态、只读（view）、无 owner、不可升级**。它不托管资金、不收集任何用户信息、不签发任何「信任分数」——证据全部在链上，任何人可独立复核。

### 2.2 两键原则（核心设计）

抗女巫需要回答两个不同的问题，我们刻意把它们分开：

| 问题 | 用什么键 | 谁来答 |
|---|---|---|
| 「这是不是一个唯一真人？」 | **地址**（address） | BeCounted 原语，每次调用现查注册表 |
| 「这个人在这场活动里算过没有？」 | **持有者地址**（与 Agent ID 一人一号、一一对应；参与记录由调用方合约按地址保存） | 调用方自己的合约保存状态、自行去重 |

原语保持无状态，活动规则（份数、时间窗、奖品）全部留在调用方——这样门禁可以被任何合约复用，而不需要信任我们维护任何状态或名单。

如实说明第二键的实现口径：去重状态在合约里按持有者地址记录——地址与 Agent ID 的一一对应正是第二键成立的前提（同一个真人换地址也变不出第二个 ID 所绑定的参与资格，因为新地址先要过第一键、且其参与记录从零开始，两键缺一不可）。当调用方需要按身份本身组织名单时，键就是 ID 名字本身：条件 5（Agent ID 名单）的默克尔叶是名字哈希，合约参加时以注册表 `handleOf` 现取现验——那是两键原则在名单场景的直接实现。

### 2.3 三条边界（写进合约注释与官网）

1. **不反查**：原语与工具只支持「地址 → 是否真人」；我们不提供「名字/name.ai → 钱包地址」的反向查询功能，也不向任何人展示解析结果。唯一例外在绑定登记：持有人本人申请自助登记时，由其自己的 Agent 在内部解析一次完成审核，解析结果不展示、不保存，项目方不经手。
2. **不判人品**：只证明「同一人、且仅一人」（可问责性），不输出信誉分、不判断任何地址是否「可信」。
3. **不查小号**：不做地址聚类或关联分析；结构性的唯一性让第二个地址天然过不了门，不需要侦测手段。

2. **参考应用 OneIDCampaigns（现行主网实例为 V18 = V17 + 第二轮深度评审三项修订（参加/投票入口重入防护、中奖权重明细事件 DrawWeights、任何人可代触发的 claimPrizeFor 代领），V17 本身 = V16 + 第一轮外部审计三项修订（加权权重锁定快照、链接完整 https:// 校验、构造器 checkIn 校验），绑定指向 BindingsV4、权重指向 CheckInV2）**：抽奖（一人一票、开奖种子在活动结束后上链锁定——任何人可调用 `lockDraw` 把种子块固定为当前块 +2，该哈希在报名期不存在、锁定者也无法预知；窗口过期可重新锁定、无兜底种子、开奖结果任何人可复算、奖品托管、中奖自助领取、30 天未领创作者回收；另支持自定义链下奖品——奖品说明上链存证、中奖名单由链上开奖产生、发起人按名单链下发放，适合白名单、实物等非代币奖品；V13 起发起人可再存一个信息收集链接（自己的表单），开奖后仅向中奖人显示，中奖人在发起人的表单里填写领奖信息——个人信息永不上链、平台不经手；该链接与说明在开奖瞬间于合约层冻结（开奖后任何修改或清空都以 WinnerInfoLocked 回滚），杜绝开奖后换链接的钓饵替换，活动页的中奖块同时显示表单目标域名与防骗提示）、投票（一人一票、2–16 选项，选项文字创建时上链存储、不可更改，可选托管奖池：结束后从全部投票人中随机抽取指定人数平分，与所投选项无关）、领取（一人一份即时到账，等额与拼手气随机两模式，随机为 blockhash 伪随机、明示仅适合小额娱乐；V15 起领取活动也可使用自定义奖品——「登记型领取」：不托管代币、不设奖池，领取只在链上记名占位、一人一份、先到先得，发起人事后按链上领取名单线下发放实物或权益，前 100 名这类场景第一次有了原生的先到先得实现；V16 起抽奖在创建时可勾选「按签到权重开奖」；V17 起权重在报名截止、lockDraw 锁定种子时快照冻结（权重 = 1 + 近 14 天签到天数），开奖只读快照、按权重比例无放回抽取——截止后的签到与开奖时机都无法再改变权重，种子机制与等概率开奖完全相同（锁种、无兜底），DrawWeighted 事件记录快照总权重、V18 的 DrawWeights 事件进一步记录每位中奖者的快照权重，任何人可用锁定区块的权重独立复算；权重由参加者自己的公开签到史决定，发起人无法设定或干预）。每个应用都在自己合约内按两键原则去重，是原语的活演示。前端在参加/投票/领取前会先预检 isHuman，非真人直接引导领取 Agent ID，不发注定失败的交易。前端同时读取 V18、V17、V16、V15 与 V14 五个实例（活动引用 v18:<编号> / v17:<编号> / v16:<编号> / v15:<编号> / v14:<编号>），历史活动与新活动在同一界面连续呈现。
2b. **赛季合约 QuestPass（真人远征）——后续扩展，不在本届提交范围**：多日赛季专用合约（7 天印记期 + 集满印记后的终章开奖，赛季形状部署时写死、资金全额托管、无 owner），已在 BSC 测试网完成部署与全流程实测（新源码试验季 0xAeC4FF16a9D59ee77079157e6F230AF1d6CE0907，单元测试与终章开奖链下复算均与链上一致）。**经项目方决定，QuestPass 不部署主网**：本届以每日签到（2c）承接回访节奏，本文不声明其主网奖池与排期。
2c. **每日签到 CheckIn（主网已上线）**：仅 Agent ID 持有人可签、每人每天一次（北京时间日切）；签到权重 = 1 + 近 14 天签到天数（现行 CheckInV2，2026-11-27 由 30 天窗口调整为 14 天以贴合活动节奏；V1 合约保留只读、其记录不再计入权重），权重函数在合约内公开、任何人可复算，签到事件（CheckedIn）上链可供独立重算。双通道：网页钱包直签，或经参与 Skill 由持有人自己的 Agent 代发（Agentic Wallet 连不上第三方网站，这是持有人侧的真实通道）。权重有两条使用路径：一是任何发起人创建抽奖时可勾选链上加权开奖（V16 引入、V17 改为锁定快照，见第 2 节）；二是平台自办的链下奖品活动（如 API 额度抽奖）按公开的权重表 + 种子 + 算法做加权开奖、全程可复算（配套只读工具 weighted-draw 逐地址把事件重算权重与合约 `weightOf` 交叉核对，不一致即判无效）。主网合约见第三节；上线次日即有第三方持有人经 Agent 通道完成签到（见 4.1）。
> **开奖种子机制（如实披露）**：V11 起，抽奖与奖池投票的种子不再由创建者在创建时选定，也没有兜底种子。活动结束后，任何人调用 `lockDraw` 把种子块固定为「当前块 + 2」——该块的 blockhash 在报名期与锁定时刻都不存在，锁定者无法预知、更无法挑选；`draw` 只能在该哈希可读的 256 区块窗口内执行，窗口一旦过期，旧锁作废、任何人可重新锁定一个新种子块（仍有效的锁不可重锁，杜绝挑种）。（QuestPass 终章为同一机制的变体，细节见其合约注释；该合约不在本届主网范围内。）

3. **链上身份层**：身份卡页（查任意地址的真人状态、参与记录、分享卡图）；X 绑定（双通道：普通钱包签名——登记合约在链上用 ecrecover 复核；Agentic 地址自助登记——固定模板推文存证 + 本人 Agent 审核 + 本人钱包上链，见第 4 层与 4.4；可换绑/解绑，证明的是同一性而非可信度）；个人主页资料（本人自填的一句话简介 + 最多 5 条链接，上链存储，页面明确标注「自述 · 未验证」，与已验证信息分区展示）。
4. **Agent 参与接口（产品本体，核心演示）**：持有人一侧没有网站入口——Agentic Wallet 不直连第三方网站，参与只能经 Agent 完成，因此本层不是附属工具，而是持有人侧的产品本体。`becounted-skill.md` 是给用户自己的 AI Agent 看的操作说明文件——用户把链接交给自己的 Agent，Agent 通过币安官方 baw 通道（开发者模式）调用活动合约（活动参加/投票/领取、自助绑定登记与每日签到全覆盖）。护栏写死在文件内：逐笔 preview、逐笔经用户明确确认才执行、一次确认只做一笔、禁止批量/定时/自动参加、禁止参加用户未点名的活动、金额以 preview 为准。我们不持有任何用户会话、不代签、不在本站提供任何配对/登录入口。**核心演示**：持有人经 Agent 的通道已在主网实证——2026-11-26，项目方自己的 Agent ID（`9nosing.ai`）与一位第三方持有人先后经本 Skill（baw 通道）完成每日签到，全程链上事件可查（见 4.1）；经 Agent 参加一场活动合约活动的完整实走仍是发招募帖之前的上线闸门，其实录回填于 4.1：`{{AGENT_MAINNET_WALKTHROUGH_RECORD}}`。 **参加条件引擎**（V7 引入、V10 新增条件 5、V11 沿用）：发行人可给活动叠加六种全部链上可验的条件——必须绑定 X、持币门槛（ERC20/NFT 按余额计）、参加过指定活动、远征印记达标、地址名单制（发行人把地址名单的默克尔根写进合约，参加者凭默克尔证明加入；名单不上链、大小不影响创建成本，任何人拿到名单都可复算根值与合约核对）、Agent ID 名单制（V10 新增：名单换成 Agent ID 名字，默克尔叶是名字哈希的再哈希；参加时合约用注册表的 `handleOf(参加者地址)` 实时取其本人名字验根——只用「地址 → 名字」这个允许方向，全程不做任何「名字 → 地址」解析。**白名单里只有身份、没有地址——名单存的是名字的哈希，连发起人也不需要任何人的钱包地址**；且名单绑的是身份不是地址快照，持有人改名即出名单）——在参加入口于真人校验之后、去重标记之前逐条执行，不满足不会消耗参加名额。「关注发行人」故意不做成条件：关注关系只存在 X 的服务器上、链上验不了；绑定条件是它的无信任版本（每位参加者都带公开账号，任何人可在 X 上对照粉丝列表核对）。绑定有两种证明并在链上如实标注（现行 IdentityBindingsV4，链上 `proofTypeOf` 可查：0 = 签名、2 = 自助登记、255 = 无绑定；V3 的见证登记 1 为历史记录、只读保留）：普通钱包走签名验证（强证明）；Agentic Wallet 无法任意签名（只支持 EIP-712、不开放 personal_sign），走**自助登记**——持有人用所绑 @ 的 X 账号发一条固定模板推文（只写 X 账号、Agent ID 名与由其地址派生的验证码，推文本身不写地址），把链接交给自己的 Agent，Agent 逐项审核（作者、模板、用持有人本人钱包地址复算验证码）后，由持有人本人钱包调用 `registerSelf` 上链登记，推文 ID 作为存证编号一并存入合约（`proofRefOf` 可查）。登记实时完成、无登记员、无人工审核、gas 由持有人自付。其证明强度如实标注：账号侧是「声明 + 公开可证伪 + 可撤销」——任何人都能对照存证推文核对；登记员在 V4 的唯一权力是撤销可被客观证伪的自助登记（存证推文不存在或作者不符，范围事前公开写死），每次撤销链上留痕，且只动绑定记录、不动 Agent ID、签到与已参加活动；地址侧由交易发送者天然证明。自助登记不得覆盖签名绑定，签名登记可升级自助登记；两次登记之间有 24 小时链上冷却（防恶意反复换绑）。

### 2.5 模式已被真实生态验证（背景证据）

「用注册表 balanceOf 做一人一份门禁」并非纸上设计：Ptah 的 Proof of Agent 及一批第三方铸造项目已经在主网用同一注册表做门禁。BeCounted 的工作是把这个已被验证的模式产品化——标准接口、开源模板、可直接接入的前端与 Agent 工具——目标是让下一个项目十分钟就能用上（接入成本为设计目标，尚无第三方接入实测——如实标注）。

### 安全审计与修复（2026-11-23，上线前深审）

上线前我们对全部托管资金的合约做了一轮逐行深审（OneIDCampaigns、QuestPass、绑定与原语的信任面），并写了 33+ 条对抗性测试探针实际尝试盗取资金（双领、重入——含恶意代币回调与 BNB 收款回调两路、越权回收、条件 0–5 绕过、Merkle 证明盗用与重放、非中奖者领奖、种子择时）。结论与处置如实记录：

- **发现 1 项 Critical 并已修复**：旧版 `claimPrize` 不检查创建者是否已回收余款、也无领奖期限——中奖者在创建者于 30 天后合法回收之后仍可再领一次，同一份奖金会从同合约其他活动的托管中付第二次（已用 PoC 测试实证：双活动池中受害活动的奖金被掏空对应份额、其余中奖者无法足额领取）。V11 修复：`claimPrize` 增加 `reclaimed` 检查与 30 天窗口的链上强制（ClaimExpired），PoC 剧本反转验证——回收后领取直接 revert，受害活动中奖者足额领回。
- **High（开奖种子时机）已根治**：旧版种子由创建者在创建时选定、且过期后走可逐块预演的兜底种子，开奖时机可被挑选。V11 改为锁种模式（见上「开奖种子机制」披露）：种子在活动结束后才上链锁定、过期可重锁、无兜底，挑选开奖块不再影响结果。
- **Medium（手续费代币）已修复**：旧版按名义金额记账，转账扣费型代币会使奖池资不抵债并锁死余款（实测量化：托管 1000、实收 900 时 900 永久锁死）。V11 的 `_fund` 按实际到账校验，短收整笔 revert——此类代币无法再创建活动（标准 ERC20 与 BNB 不受影响）。
- **其余探针全部被挡**：双领、两路重入、越权/提前回收、条件绕过、证明盗用、非中奖者领奖均未成功；QuestPass 账目逐 wei 精确、59 USDC 每一分都有合法出口；信任面无 fail-open（登记员密钥泄露最坏只能伪造/撤销「见证」级绑定，够不到奖金）。
- **残余信任与局限（如实）**：全栈继承对 SPACE ID 官方注册表与 USDC 发行方的信任；即时拼手气随机为娱乐级伪随机（可提前算出自己的下一笔金额，影响封顶于约 2 倍日均值、总池不变）；持币门槛条件为参加瞬间快照语义，可被闪电贷冲过，但每人一次的去重不受影响。

## 四、对评分四项的自述（实事求是版）

### 4.1 Agent ID 应用深度（权重 30%）

我们对 Agent ID 的使用不是「查一下有没有」就结束，而是把它做成三种可复用形态、覆盖四类使用者：

- **合约层**：`isHuman` 原语 + GatedClaim 模板，任何合约一行接入；
- **网页层**：官网内置查真人工具，普通用户输入地址即可验证（读主网注册表，已实测项目方自己的 `9nosing.ai` 持有地址返回 true）；
- **Agent 层**：只读 MCP server / CLI 供 AI Agent 调用校验；参与 Skill 让用户的 Agent 经币安官方 baw 通道、在钱包层强制确认下参加活动——Agent 的链上调用者就是 Agent ID 地址本身，能过门禁、计入交互。
- **身份层**：绑定与名片都以 Agent ID 持有地址为锚，参与记录、可问责性都沉淀在同一身份上。

两键原则保证深度不是堆功能：原语无状态、职责单一，去重状态归调用方，这是能被别人真正复用的前提。

### 4.4 创新性（权重 20%）

- **把「唯一性」从规则变成结构**：一人一份不靠事后筛查，而由 KYC 锚点在合约入口处强制执行——这是 Agent ID 区别于普通 NFT 门禁的根本点，我们的产品完整建立在它之上。
- **两键原则**：把「是不是真人」（地址问原语）与「算过没有」（ID 归调用方记）拆开，是据我们所知首个把该分工写成公开设计原则并落进合约与文档的参赛实现；它让原语能保持无状态、可被任意合约复用。
- **可复算的公平**：抽奖种子在活动结束后上链锁定（`lockDraw` 固定当前块 +2 的哈希——报名期不存在、任何人无法预知或挑选）、结果由任何人用链上数据一键复算验证，把「公平」从承诺变成可检验的事实。
- **Agent 原生**：只读校验 MCP 与受护栏约束的参与 Skill，让「Agent 先验真人、再替用户办事」成为可落地的标准动作，而不是概念图。
- **创新展品：为不能签名的钱包设计的自助登记（IdentityBindingsV4）**：Agentic Wallet 只支持 EIP-712、不开放任意签名，传统的「签个名证明这个 X 账号是你的」对它天然不可用——这是我们在真机实测中撞上的真实平台约束。第一代解法（V3 见证绑定）靠登记员核对推文后上链：能跑，但慢、要排队、还引入一个人工信任点。V4 把审核员换成持有人自己的 Agent：验证推文是固定模板，每个变量要么在链上、要么可由持有人本人地址复算，Agent 逐项核对一致后由持有人本人钱包直接上链登记，推文 ID 存证进合约——登记从「等人工队列」变成 1–2 分钟实时完成，登记环节里没有任何第三方。证明强度如实分级：签名（强，链上密码学复核）> 自助登记（声明 + 公开可证伪 + 登记员仅可撤销存证推文不存在/作者不符的可证伪登记，范围事前写死、撤销链上留痕）> 无绑定；自助登记永远不得覆盖签名绑定，另配 24 小时登记冷却防反复换绑。

我们不声称自己是「标准」或「唯一」——只说：我们最先把这个锚点做成了任何人可直接调用的接口，并用一套完整产品证明它能跑通。
